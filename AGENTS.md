## Before edits

1. Verify the Git root and canonical `origin`.
2. Fetch and record current `origin/main`.
3. Inspect the branch, worktree, recent relevant commits, overlapping pull requests, branch protection, and required checks.
4. Preserve unrelated owner work. Use a clean branch or worktree based on current `origin/main`. Never push directly to `main`.
5. Define outcome, behavior, scope, exclusions, acceptance criteria, risks, rollback or fail-closed behavior, and validation.
6. Stop when identity, base SHA, scope, ownership, approval, protected boundaries, or irreversible effects remain unclear.

Keep branch protection and required checks enabled. Do not modify other assistant instruction or settings files unless the owner requests that exact change.

## Risk and workflow

- Low: clear, narrow, reversible, with no material formula, data, factual public claim, accessibility, privacy, security, commercial, publication, provider, deployment, or architecture effect. Work directly with one main agent.
- Medium: unfamiliar behavior, multi-file work, material user behavior, or meaningful regression risk. Use `$ft-plan`. Use `$ft-debug` when the cause is unproven.
- High: formulas, canonical data, factual public claims, structured data, privacy, analytics, security, publication, payments, providers, delivery, databases, retention, StitchProof, deployment, production, or irreversible actions. Use `$ft-plan`, focused regression coverage, `ft_reviewer`, `ft_verifier`, and every applicable required check.
- Use `$ft-run` only for an approved `.codex/TASK.md`.
- Use `$ft-audit` for TRUTHMODE, progress, final review, or next actions.

A bug fix must reproduce the defect and add a failing regression test first when practical. Confirm the expected failure. Otherwise record why and define repeatable alternate proof. A disappearing symptom is not root-cause evidence.

Make the smallest complete change. Search exact paths, symbols, references, and tests first. Reuse verified patterns. Avoid unrelated cleanup, refactors, renames, formatting, and dependencies.

Use one main agent normally. Spawn no more than two agents, excluding the primary. A read-only explorer is for independent mapping only. Close it after handoff before starting reviewer and verifier. Use `ft_reviewer` for substantial medium-risk work and both independent agents for high-risk or final release-sensitive work. Never give writers overlapping files. The parent owns scope, file ownership, integration, and the final report. An implementer never approves its own work. Resolve reviewer and verifier disagreements against direct evidence. Close every subagent after its result is captured.

Use one temporary `.codex/TASK.md` for multi-turn work. Keep it concise, link to paths, preserve final evidence in the pull request or proper tracked record, then delete it.

## Validate and report

Run the smallest relevant test while editing. Run each applicable broad suite once after stabilization, then only after a relevant change or failure. `.github/workflows/empire-check.yml` is full CI authority.

Before commit or promotion:

1. Inspect `git diff --check` and the complete diff.
2. Exclude unrelated files, secrets, private products, artifacts, and protected records.
3. Run focused regression tests and every applicable required gate.
4. Complete required independent review and verification.
5. Record exact commands and observed results. Mark skipped, blocked, timed-out, flaky, and untested checks.
6. State residual risks, rollback, and the next owner action.

Report separately: local change; focused tests; pushed branch; pull request and checks; merge; SHA-tied deployment; direct production verification. Never use one stage as proof of a later stage. Use `Verified`, `Inferred`, `Unknown`, `Blocked`, and `Not tested`.

## Code Review Rules

Give the exact file, line or symbol, failure mode, impact, and narrow safe correction.

- P0: protected-record or secret exposure, personal or payment data exposure, data loss, unauthorized access, irreversible financial action, unapproved production or provider action, or fabricated approval, readiness, customers, demand, or revenue.
- P1: incorrect behavior, formulas, bounds, claims, dates, attribution, or structured data; publication bypass; privacy, consent, security, payment, or accessibility regression; missing material regression coverage; or false release-stage claims.
- P2: material recovery, documentation, performance, dependency, abstraction, edge-case, or maintainability risk. Ignore style-only preferences.

## Done

Complete means identity and base were verified; scope, exclusions, criteria, risks, and validation are explicit; implementation matches scope; regression coverage exists; every matching policy and exact record was followed; claimed checks have evidence; required findings are resolved; the diff is clean; residual risks and untested areas are stated; and the exact release stage and next owner action are clear.

Code complete does not mean merged, deployed, activated, delivered, or production-verified.
